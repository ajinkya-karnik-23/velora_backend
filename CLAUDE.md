# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

CIQ (Controls Internal Quality) Backend — an audit management API built with FastAPI, async SQLAlchemy, and PostgreSQL. All 5 phases are implemented: auth/users, clients/versions, review cycles/engagement teams, controls/config controls, and evidence/test logs.

# Run with Docker (includes Postgres + Azurite)

## Architecture

**Layered pattern**: Endpoint -> Service -> Repository -> Model

- `app/api/endpoints/` — FastAPI routers. Each file is a resource (auth, users, clients, versions, review_cycles, controls, control_tests, evidence, test_logs).
- `app/services/` — Business logic. Services own transaction boundaries (commit/rollback). Named `{resource}_service.py`.
- `app/repositories/` — Data access. All extend `BaseRepo[ModelT]` which provides generic CRUD. Repositories **never call `session.commit()`** — only flush.
- `app/models/` — SQLAlchemy 2.0 declarative models. All use `BigIntTimestampMixin` for `created_time`/`updated_time` as Unix epoch integers.
- `app/schemas/` — Pydantic v2 request/response schemas.

**Key cross-cutting modules:**

- `app/api/deps.py` — FastAPI dependencies: `get_db()`, `get_current_user()`, `require_role()`, `require_permission()`, `require_engagement_member()`. Role hierarchy: Viewer(0) < Auditor(1) < Moderator(2) < Admin(3).
- `app/core/config.py` — `Settings` (pydantic-settings), loaded from `.env`. Singleton `settings` used throughout.
- `app/core/security.py` — bcrypt password hashing (cost 12), JWT access/refresh token creation and verification.
- `app/core/exceptions.py` — `AppException` base with subclasses (`NotFoundException`, `ConflictException`, `ForbiddenException`, `UnauthorizedException`). All return structured JSON `{"error": {"code", "message", "field"}}`.
- `app/db/base.py` — Model import hub. All models must be imported here for Alembic autogenerate to detect them.
- `app/db/session.py` — Async engine and session factory (`asyncpg`).
- `app/middleware/rate_limit.py` — Rate limiting middleware.
- `app/middleware/request_logging.py` — Request/response logging middleware.

**Infrastructure:**

- PostgreSQL 16 (via asyncpg), Azure Blob Storage (Azurite for local dev)
- Alembic for async migrations — `env.py` reads `DATABASE_URL` from app config, not `alembic.ini`
- Pre-commit hooks: black, ruff (with `--fix`), mypy
- Prometheus metrics exposed at `/metrics`, health check at `/health`

### Client data

Control definitions, the evidence vault, testing outputs and report templates are **client-supplied**: they are not part of the application, and `CLIENT_DATA_PATH` is the single variable that locates them.

```
<CLIENT_DATA_PATH>/
  control_jsons/              control definitions, one JSON per control
  supporting_documents_dump/  evidence vault, one folder per control number
  test_outputs/               per-control testing output JSONs
  misc/                       report templates + config JSONs
    dummy_template.xlsm             empty TWP work paper
    twp_template_map.json           empty/completed TWP per control
    sampling_matrix.json            frequency x risk/round -> sample size
    sampling_metadata.json          per-control sampling reasoning
    evidence_filename_map.json      expected evidence filename per control
```

On the **`poc-2` branch this folder is committed as `poc-2-data/`** so the POC can be cloned and run as-is. That is a branch-specific choice — a real deployment points `CLIENT_DATA_PATH` at its own copy and leaves the folder untracked.

Each path (`CONTROL_JSONS_PATH`, `SUPPORTING_DOCS_PATH`, …) can be set individually to override the value derived from the root — see `app/core/config.py`. An explicit environment value always wins.

The app starts and runs without this data: every loader degrades to an empty result, the demo-vault static mount is skipped rather than aborting startup, and the affected screens come up blank. Tests that read the real files skip when it is absent (`tests/client_data.py`).

> Two files store paths **in their own contents** — `twp_template_map.json` and the seeded `clients.evidence_vault_path` / `control_jsons_path` columns. Renaming or relocating the folder means updating those too, not just the environment.

## POC-specific behaviour (Arcelor Mittal / `poc-2`)

This branch carries a client demo layered on the generic platform. The pieces worth knowing before changing anything here:

- **The testing-output JSON is the source of truth for verdicts.** `Run` in the Testing UI is a presentation-only reveal — it plays an executing state and then shows the result already stored in `test_outputs/`. Nothing is computed and the testing output is never modified. Each finished run is recorded in `test_logs` for the audit trail via `POST /api/v1/test-logs/record-sample-run`: the client sends only the control and sample number, and the server looks the verdict up (an invalid evidence upload is logged as `EVIDENCE_EXCEPTION` with a generic note). Recorded manual-step results are logged too. `test_logs.source` is `sample`, `manual_step`, or null for pipeline and older rows. Note that **Clear Run Data deletes a cycle's test logs**, which removes these audit entries as well.
- **Per-sample evidence gating.** `check_evidence` judges each sample on *its own* uploads against `evidence_filename_map.json`; a valid file on a sibling sample never vouches for another. Messages are deliberately generic and must never reveal the expected filename. `get_evidence_pages` applies the same gate.
- **Matching is on content, not filenames.** `control_matching.py`, `test_output_matching.py` and `twp_templates.py` all resolve by control number + entity code read from the file, accept any extension, and degrade quietly when a file is missing or malformed. Follow that pattern for new client-data loaders.
- **Per-client isolation.** `Client.evidence_vault_path` / `control_jsons_path` scope each client to its own data, so the Signora seed client keeps working alongside the POC client.
- **Review workflow** (`control_review_status`, `control_review_events`; migration `e7a9c1d3b5f4`; service `control_review_service.py`; routes under `/review-cycles/{id}`: `review-status`, `review-events`, `submit-for-review`, `submit-many-for-review`, `review-verdict`). Only the hand-over and the reviewer's verdict are stored — one row per attached control. The tester-side states (pending, in progress, processed) are **derived from testing progress in the UI** and never written, so they cannot drift from the samples. Submitting again is allowed for a returned control and clears the previous verdict; returning requires a note. Every transition is appended to `control_review_events`, which keeps the trail after the status moves on.
- **Knowledge base per client.** `app/api/endpoints/kb.py` serves markdown from `velora_kb/` by default, or from a client's own folder when mapped in `_CLIENT_KB_DIRS` (ARCELOR-MITTAL → `velora_kb_sox_poc2/`, 31 articles). Articles use frontmatter (`level`, `nodeType`, `color`, `icon`) and `[[Title]]` links. The SOX POC 2 knowledge base is illustrative and not used by testing.
- **Default evidence.** `misc/default_evidence_map.json` lists, per control, where its evidence lives (`poc-2-data/files/...`) and how files map to samples (`fixed`, `filename_rule`, or `evidences_used` with an optional per-sample `folder_field`). The Testing card's **Auto-attach evidence** button calls `GET /review-cycles/{id}/default-evidence` (status) and `POST .../attach-default-evidence`, which attach any missing file for that one control, one row per sample (`services/default_evidence.py`). A file is present when the test and sample already hold that file name, whoever uploaded it; nothing is removed. The IA5.CA04 and IA5.CA01 files are empty placeholders.
- **TWP summary narrative.** `control_details.template_summary` in a control JSON (two paragraphs: nature of testing, then results and root cause) is appended under the computed headline in the completed TWP's "Summary of test performed" box (D147), and the box's lower row is grown to fit. Re-run `build_twp_completed` after editing it.
- **Scope summaries.** A control JSON may carry `control_details.scope_summary`: plain text, with sections separated by a blank line, each opening "Label: …", and list items starting "- ". `control_matching.scope_summaries()` reads it from the client's JSONs on disk each time, and both the cycle controls listing and the Control Repository (`ControlOut.scope_summary`) use that before any stored snapshot, so edits show without re-attaching or re-importing. The **View scope** button in both tables opens it.
- **Manual test steps** (`manual_test_steps`, `manual_test_step_results`, `evidence_files.manual_step_id`; service `manual_test_step_service.py`, routes `/api/v1/manual-test-steps/*`). Auditor-defined procedures on a control. A step with `config_control_id` set belongs to one cycle; null means it is kept on the control and applies to every cycle attaching it. Verdicts are recorded by the auditor per step per attached control, and each is pinned to a server-computed fingerprint of the step's evidence in that cycle: `list-for-cycle` omits a result once that evidence changes. Step evidence carries `manual_step_id` and **no `test_id`**, so it never enters sample evidence gating. Deleting a step unlinks its evidence rather than deleting files; clearing a cycle's run data also clears step results. The completed TWP workbook is pre-built and does not include manual steps.
- **Sampling modes** (`review_cycles.sampling_mode`, `is_locked`; `config_controls.selected_samples`, `not_tested_reason`; migration `f2b4d6e8a0c1`; `services/matrix_sampling.py`). `full_population` tests every sample in the testing output (the original behaviour). `matrix` sizes each control from the sampling matrix only — a range takes its upper bound, no fallback to the control JSON's own "Sample Size" — splits the count across sample types in proportion to the population (types come from `methodology.breakdown`, else the NR/manual split) and spreads the picks evenly; `get_test_output` then returns only the selection, with `population_count`. A control with no population (either mode) or no matrix size (matrix mode) gets `not_tested_reason` and no samples. `GET /review-cycles/{id}/sampling-check` reports selected vs available per control and type; `PUT .../sampling-mode` switches and re-samples. A locked cycle refuses delete, control removal and mode changes. `scripts/setup_matrix_sampling_cycle.py` locked cycle 16 ("Q1 Sox review") and created cycle 17 (its matrix twin) — never delete or re-size cycle 16.
- **Document references** (`evidence_files.doc_ref`, unique per cycle; `services/doc_refs.py`; migration `a3c5e7f9b1d2` backfilled existing rows). Every creation path (upload, vault import — which now takes `sample_no` — and auto-attach) calls `assign_doc_ref`: `<control>-S<sample>-D<n>`, `-T<step>-` for manual-step evidence, never reused.
- **Per-cycle TWP.** `services/twp_builder.py` holds the work-paper fill (the script now only saves its output). The download builds the completed — or not-tested — paper live with a `TwpContext` from `services/twp_context.py`: the cycle's own samples, tester judgements, document references per sample, untested sample types, and a "Testing Sign-off" sheet (tester/reviewer names and dates). A round still in progress shows only the samples it has run; the rest read Pending (the testing output's stored verdicts are not revealed early). The paper reads the control JSON through `with_demo_changes`, so IA5.CA03.1 shows Annual. The static `*.TWP.Completed.xlsm` files remain the fallback.
- **Untested sample types** (`config_controls.untested_types`): a matrix split that gives a type no sample records it with the reason; surfaced in the sampling check (`partial`), test output, TWP and dashboards.
- **Tester judgements** (`sample_judgements`, migration `b4d6f8a0c2e3`, `services/sample_judgement_service.py`, routes `PUT/DELETE /review-cycles/{id}/sample-judgement`, `GET .../sample-judgements`). The testing output's `result` stays the tool's; a judgement (`accepted`/`modified`, conclusion, root-cause category for a failure) rides beside it on each sample as `judgement`, is logged to `test_logs` with source `judgement`, and is cleared by Clear Run Data. A change needs a conclusion; a FAIL needs one of the five `ROOT_CAUSE_CATEGORIES` (models/sample_judgement.py).
- **Sample reviews** (`sample_reviews`, `sample_review_events`; migration `e9b1d3f5a7c8`; `services/sample_review_service.py`; routes `PUT /review-cycles/{id}/sample-review`, `GET .../sample-reviews`, `GET .../sample-review-events`, `GET /review-cycles/notifications?client_id=`). The reviewer's word on one sample: a changed outcome (PASS/FAIL/NOT_VALIDATED), conclusion, comment, people involved and a verdict (the control verdict set). Each changed part is an event. The reviewer's outcome overrides the tester's judgement wherever results are read: `TestSampleOut.review`, `PhaseService.results`, the cycles overview and the TWP (`apply_judgement`). Notifications combine control review events (reviewer verdicts → tester; tester hand-overs → reviewer) with sample review events. Clear Run Data clears both tables.
- **Review Cycles overview** (`GET /review-cycles/cycles-overview?client_id=`, `services/cycle_overview_service.py`): per cycle, results by control from the audit trail (a sample counts once its run is logged; a tester judgement overrides the logged result), control profile (process, nature, risk, frequency, key, IPE), team, testers, reviewer and runs per day. **Demo activity:** `misc/cycle_activity.json` (`CYCLE_ACTIVITY_PATH`) can supply the team, tester shares and per-day activity for a cycle it matches; the response then sets `demo_activity` and the UI labels it.
- **Vault manifest** (`<vault>/vault_manifest.json`, `services/vault_manifest.py`). When present it defines what the Evidence Vault lists per control. Only an entry with a `path` is a real document — it alone can be viewed (`demo-vault/download`) or linked to a test (`import-demo-file`); listing-only entries return 403 and the UI shows a lock. The same rule governs attached evidence: `EvidenceService.is_viewable` sets `EvidenceOut.viewable` and `download_stream` (used by download and the Testing tab's evidence pages) refuses anything else with 403. For ArcelorMittal only IA8.CA02's `JV's TOE.pdf` is viewable; the other controls' entries mirror the file names in `files/test_files/`.
- **Testing phases** (`control_phase_runs`, `control_phase_events`; migration `c6e8a0b2d4f6`; rules `app/core/phase_rules.py`; service `services/phase_service.py`; routes under `/review-cycles/{id}`: `phases`, `phase-sample-size`, `phase-fail`). Matrix-sampled cycles only — the full-population baseline (cycle 16) is never phased. A control runs DE → OE → RF, and an annual control adds YE after RF (DE → OE → RF → YE, YE sized from the matrix's YE column — 1 for Annual); each run is one round of a phase with its own size, evidence window and selection, and a failed run opens an RM round (`remediates_run_id`, `attempt`) on fresh samples from the same window. Sizing: DE = 1 always (`DE_SAMPLE_SIZE`), OE frequency × risk, RF/RM/YE their column by frequency only, population bands for upon-occurrence; a tester override (any phase but DE) is refused above what the window can draw, without naming the limit. The current run's selection is written to `config_controls.selected_samples`, so `get_test_output` and everything keyed by sample number (evidence, logs, judgements) need no run id — sample numbers are never reused across runs. `get_test_output(..., phase_run_id)` reads an earlier run. The review workflow stays per control: approval in `ControlReviewService.record_verdict` advances the control (`PhaseService.on_verdict`) and clears the review row for the next phase; Clear Run Data resets every control to DE. `misc/phase_demo.json` (`PHASE_DEMO_PATH`) is the demo scenario layered over the testing output for phased cycles only (`pins`, `exclude`, per-sample overrides — IA4.CA14 fails DE and RF on a wrongly uploaded document); the testing output files are never changed. **Testing calendar (FY2026):** cycle 17 runs 1 May 2026 – 31 Jan 2027; DE is tested in May, OE September–October, RF December and YE (the year's close) the following January, and each phase's evidence window is the same months (`EVIDENCE_WINDOWS`; planned slots `TESTING_CALENDAR` → `planned_window`, at midday UTC so dates read the same in any timezone). The documents themselves date from Jan–Jul 2025: `services/demo_calendar.py` moves every date a phased sample shows (date fields, `Month`, yyyymmdd `Assignment`, dates quoted in the validation text) through `phase_demo.json`'s `calendar` segments (Jan→May, Feb–May→Sep–Oct, Jun–15 Jul→Dec, 16–31 Jul→Jan 2027), inside `load_phased_output`, so drawing, the Testing tab, evidence map, TWP and CRP all read the shown dates. The mapping is monotonic, so draws are unchanged. File names are never changed (also not inside the text); a moved field's original value rides on the sample as `source_fields` (`TestSampleOut.source_fields`), which the evidence filename rule reads (IA5.CA03.1's monthly reviews are filed `Apr-25.pdf`). Attaching a control to a matrix cycle applies `with_demo_changes` to its snapshot, so IA5.CA03.1 stays Annual after a re-attach. Per-phase downloads: `reports/twp-template?phase_run_id=` per control, and the CRP per phase for the whole cycle — `reports/crp-phase?cycle_id=&phase=`, refused with `PHASE_NOT_COMPLETE` until every control on that phase has its final round approved, named `CRP_<cycle>_<PHASE>_Completed.xlsx` — plus `reports/crp-final` and `reports/twp-final` (a zip of every control's TWP per phase, final round) once the whole cycle is approved. See **CRP workbook** below. (`build_cycle_crp_workbook` in `crp_builder.py` is the old placeholder, no longer served.) The older per-control `reports/crp` (`services/crp_builder.py`, placeholder format) remains but the UI no longer offers it. Per-control files are named `TWP_/CRP_{control}.{entity}_{PHASE|RMn-PHASE}_{Completed|In_Progress}`. `scripts/setup_phased_cycle.py` resets the matrix cycle to DE and renames the demo account to Anshu Sharma.
- **Phases run in sync across a cycle.** `PhaseService.cycle_phase` is the earliest phase any attached control still has to clear (`first_needed`, order `CYCLE_ORDER`). On approval a control's next phase opens only when it equals the cycle phase; otherwise the control waits (a `waiting` phase event, `ControlPhasesOut.waiting_for`), and `_release` opens it for every waiting control once the last control clears the phase. `CyclePhasesOut.cycle_phase` reports it. Runs already active are untouched. A run's results count only logs dated after it started (`PhaseService.results`): test logs are keyed by control and cycle, so they outlive a detach/re-attach, and a re-attached control must read untested; likewise a round returned by the reviewer counts only runs after the return (and the return clears `testing_started_*`). The cycles overview applies the same rule (runs before a control's `created_time` are ignored), and `cycle_activity.json`'s illustrative run activity is applied only to the locked demo cycle. `GET /review-cycles/{id}/evidence-map` (`services/evidence_map_service.py`, read-only) dates every population sample (`phase_demo.sample_date`) with the run that drew it, its result and the files attached.
- **CRP workbook** (`CRP_TEMPLATE_PATH` = `misc/Concurrent Review Process 2026 - AME FZCO- TOE.xlsx`; `services/crp_template.py` fills, `services/crp_report.py` reads the platform). The client's workbook, edited at the XML level so its styles, dropdowns and conditional formats survive (openpyxl would drop the dropdown/conditional-format extensions). Sheets: Test of Design = DE, Operating Effectiveness = OE, Rollforward = RF, Year End = YE (`scripts/add_crp_year_end_sheet.py` added YE to the client's file as a copy of Rollforward, 2026-10-28; idempotent). **Every phase sheet lists only the cycle's controls**: the list is rewritten from its first row (YE: annual controls only), the rest of the client's 38-control list is emptied (numbers kept) and hidden, the template's saved filter (it hid exactly our Test of Design rows) is cleared, and the notes under the list are replaced by the cycle's scope (`scope_notes`). A complete phase gets full rows (`crp_rows`); a phase still to come shows identity only (`identity_rows`: name, frequency, type, IPE; the rest on "Please select…"). Full rows, from the phase's final round: frequency (template words), type, IPE (`twp_builder.has_ipe`, also used by the TWP's D15), documents downloaded, test performed, test result (Effective / Ineffective when the phase failed — remediation noted — / No population), tester, the reviewer checks the platform can make from its own TWP (mandatory fields, IPE section, preparer identified, method and sample count — only OE is held to covering every sample type; DE's one sample and RF/YE's small fixed counts never flag a missing type), a review comment (AB: "No action needed. Reviewed by … : n/n samples tested (basis), exceptions, references, sign-off", or each Needs Action, plus reviewer returns with their notes, reviewer sample comments and remediation), and the Needs Action follow-up. **Cell notes** (Excel comments, author "Velora"; comments part + VML drawing per sheet) carry the detail: Documents downloaded → evidence window and each sample's document references; Test performed → round, preparer and submission, reviewer and conclusion, size basis and the run's event trail; Test result → each sample's outcome with the testing output's validation text, tester judgements and reviewer remarks (a remediated phase also lists the failed round and its reason). **Demo comments:** `misc/crp_comments.json` (`CRP_COMMENTS_PATH`, `crp_report.comment_for`) holds a short tester and reviewer comment per control and phase (a `remediated` variant for a phase that failed and was remediated); the comment column reads "Tester: … / Reviewer: …", then any return ("Returned <date>: note — corrected"), reviewer sample remarks and "Needs Action: …" lines, and the Test performed note opens with the same two comments. Optro and TeamMate+ columns stay on "Please select…". The Introductory Page gets the BPM code (F14) and the approving reviewer (F16).
- **CORS exposes `Content-Disposition` and `X-TWP-Variant`** (`app/main.py`), so downloads keep the server's file names.
- **Changing a verdict** (`ControlReviewService.record_verdict`): a verdict can be recorded again while the review row exists. Replacing an **approval** on a phased cycle first calls `PhaseService.reopen_approval` — the last approved run goes back to active (event `reopened`) — so the new verdict lands on that round; refused with `PHASE_MOVED_ON` once any control in the cycle has a run in a later phase.
- **Computed counts** (`control_phase_runs.size_computed_time`, migration `f1a3c5e7b9d0`, `PUT /review-cycles/{id}/phase-size-computed {phase_run_id, computed}`): the Controls table's Compute is a presentation step, recorded on the run so it holds in every browser; cleared by the column reset. The sampling check reports `awaiting_size` (with 0 selected) when the matrix gives the phase no count.
- **Redrawing a run's samples** (`POST /review-cycles/{id}/redraw-samples`, `PhaseService.redraw`): the active run keeps its size and window; a `redrawn` event records the samples it held, the selection is cleared and re-planned with a seed that includes the redraw count, setting aside every sample held before (while enough remain) and ignoring demo pins; a `redrawn_to` event records from → to. Refused while the control is with the reviewer. Choosing by hand: `services/manual_selection.py` — `GET .../selectable-samples` lists the population as vault collections (`VC-<control>-<nnn>`, each sample's planned default-evidence files) with whether each can be chosen (in the run's window, unused by other runs); `PUT .../select-samples {sample_nos}` sets the run's selection (exactly its size, only choosable collections), logged as `redrawn` / `redrawn_to` with `manual: true`.
- **Testing start** (`config_controls.testing_started_time/_by/_by_name`, migration `d8f0a2c4e6b8`, `POST /review-cycles/{id}/start-testing`): records when the tester started the control's current round, once; on a phased cycle it also logs a `testing_started` phase event. Cleared when a new phase run starts and by Clear Run Data.
- **Demo field changes** (`phase_demo.json` → `demo_changes: {field: {from, to, note}}`, `phase_demo.demo_changes_for` / `with_demo_changes`). IA5.CA03.1 is made **Annual** (from Monthly) so the cycle shows YE. The startup seed and control import pass every definition through `with_demo_changes`, so the change survives the repository being refreshed from the unchanged control JSONs; `scripts/apply_demo_changes.py [--revert]` also writes it to already-attached controls' `entity_detail_json` in matrix cycles (the locked baseline keeps its snapshot). `ControlOut`, `ConfigControlOut` and `ControlPhasesOut` carry `demo_changes` so the UI marks the value. `PhaseService.sizing_params` sizes every phase but YE with the original frequency (OE 2 to 5, RF 1 from Monthly), YE with the new one; the sampling check explains the same row. `ConfigControlOut` also carries `owner_name`/`owner_role` (demo owners).
- **Demo control owners** (`misc/control_owners.json`, `CONTROL_OWNERS_PATH`, `services/control_owners.py`): `ControlOut.owner_name`/`owner_role` show a named owner per control (unlisted controls take a stable pick from the roster); without the file the recorded account is shown. `ControlOut.phase_path` and `phases` (the control's state on the client's latest phased cycle) feed the repository's Phases column.
- **Demo testing team.** `scripts/assign_demo_testers.py` creates Rohan Mehta, Priya Nair and Karan Joshi as accounts that cannot sign in (random password, status Inactive) and spreads existing test logs across them and Anshu Sharma (~70% Anshu), by a hash of the log id. New runs record the signed-in user.
- **`scripts/build_twp_completed.py`** regenerates the completed TWP work paper from the control JSON, sampling matrix and testing output. Re-run it after editing any of those. It also appends a "Sample Testing Details" sheet (`app/services/twp_sample_details.py`): one row per sample, a column per parameter, then Result, Remarks and Testing Details (validation, evidence used, performer — "Velora Admin" by default).
